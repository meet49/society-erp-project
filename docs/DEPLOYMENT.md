# Deployment

## Environments

The API reads its configuration from environment variables validated by `apps/api/src/config/env.ts`.
Copy `apps/api/.env.example` to `apps/api/.env` for local development. In production set the variables
on the host / orchestrator and **never commit** real secrets.

Required in production:

| Variable | Purpose |
|---|---|
| `MONGODB_URI` | MongoDB connection string. A replica set is strongly recommended (transactions for atomic society + admin creation, bookings, journals). |
| `REDIS_URL` | Redis for BullMQ jobs and multi-instance cache invalidation. |
| `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` | ≥ 16 random characters each; rotate by redeploying (all sessions end). |
| `SIGNED_URL_SECRET` | Signs private file download links. |
| `ENCRYPTION_KEY` | ≥ 32 characters; encrypts stored gateway credentials. Losing it makes stored credentials unreadable. |
| `APP_URL`, `API_URL`, `CORS_ORIGINS` | Public URLs of the web app and API; CORS is an allow-list. |
| `TRUST_PROXY=true` | When behind nginx / a load balancer (correct client IPs for rate limiting and audit). |

Optional integrations: `STORAGE_DRIVER=s3` + `S3_*`, `EMAIL_DRIVER=smtp` + `SMTP_*`,
`WHATSAPP_DRIVER=meta` + `WHATSAPP_META_*`, `PUSH_DRIVER=webpush` + `VAPID_*`,
`PAYMENT_DRIVER=razorpay` + `RAZORPAY_*` (platform subscription payments; societies configure their
own gateway credentials in Settings → Payments).

Generate secrets:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

## Docker Compose (single host)

```bash
cp apps/api/.env.example .env      # edit JWT_*, SIGNED_URL_SECRET, ENCRYPTION_KEY, SEED_SUPER_ADMIN_PASSWORD
docker compose up -d --build
```

Services: `mongo` (replica set `rs0`, initialised by `mongo-init`), `redis`, `api` (port 4100),
`worker` (BullMQ processors + schedules), `web` (nginx on port 8080 serving the PWA and proxying
`/api` and `/socket.io` to the API).

The API runs its idempotent bootstrap at every start (module catalogue, permissions, platform
settings, default plans, landing content, SUPER_ADMIN). Run the demo seed once if wanted:

```bash
docker compose exec api node dist/seed.js
```

## Render & Vercel

### What can run where

The API is a long-lived process: it holds Socket.IO connections and, without Redis, runs the
background job schedule in-process. That rules out Vercel's serverless functions, where each request
is short-lived and nothing survives between invocations. Host the API on Render (or Railway, Fly,
any container/VM host) and put the static PWA wherever you like.

| Piece | Render | Vercel |
|---|---|---|
| API (`apps/api`) | Web Service, Node runtime | not supported |
| Web (`apps/web`) | Static Site | Static build |
| MongoDB | external (Atlas) | external (Atlas) |
| Redis (optional) | Key Value instance | external |

### Option A: both on Render (blueprint)

`render.yaml` in the repository root declares the API service and the static site.

1. Render Dashboard → **New → Blueprint** → pick this repository. Render creates
   `society-erp-api` and `society-erp-web`.
2. On the API service set the variables marked "needs a value": `MONGODB_URI`,
   `SEED_SUPER_ADMIN_EMAIL`, `SEED_SUPER_ADMIN_PASSWORD`. The JWT, signed-URL and encryption secrets
   are generated by Render.
3. When both services have URLs, fill in the cross-references and redeploy:
   - API: `API_URL=https://society-erp-api.onrender.com`,
     `APP_URL=https://society-erp-web.onrender.com`,
     `CORS_ORIGINS=https://society-erp-web.onrender.com`
   - Web: `VITE_API_URL=https://society-erp-api.onrender.com` (no trailing slash)
4. Redeploy the static site after setting `VITE_API_URL`. It is compiled into the bundle at build
   time, so changing it needs a rebuild, not a restart.

### Option B: API on Render, web on Vercel

Deploy the API as in Option A, then import the repository into Vercel. `vercel.json` sets the build
command, output directory and SPA rewrites. Add one environment variable in the Vercel project:

```
VITE_API_URL = https://society-erp-api.onrender.com
```

Then add the Vercel domain to the API's `CORS_ORIGINS` and `APP_URL`, and redeploy the API.

Do not proxy `/api` through Vercel rewrites. It works for plain requests but not for the WebSocket
upgrade, so realtime silently degrades to long polling. Point the browser straight at the API origin
with `VITE_API_URL` instead; the API already sends the right CORS headers for it.

### After the first deploy

- **MongoDB Atlas network access**: allow Render's outbound addresses, or `0.0.0.0/0` while testing.
  A blocked cluster shows up as a failing health check, not a crash.
- **Seed the platform**: bootstrap data (modules, permissions, plans, templates, super admin) is
  written automatically at every API start. `SEED_DEMO_DATA=false` keeps the demo society out of
  production; run `node apps/api/dist/seed.js` from a Render Shell if you do want it.
- **Sign in and change the super admin password** immediately.
- **Uploads**: the container filesystem is replaced on every deploy. The blueprint attaches a 1 GB
  disk at `/var/data` for `STORAGE_DRIVER=local`. For anything real, switch to `STORAGE_DRIVER=s3`
  and set the `S3_*` variables; then the disk can go.
- **Instance count**: keep it at 1 unless you add Redis. Socket.IO has no Redis adapter wired here,
  so a second instance would only reach the clients connected to it, and both instances would run
  the job schedule.
- **Free tier**: Render free services sleep after 15 minutes idle. Sleeping stops every scheduled
  job, so invoices, reminders, SLA escalation and the emergency sweep stop with it. Use a paid
  instance for anything but a demo.
- **Redis**: setting `REDIS_URL` moves jobs to BullMQ. Then also run a background worker service with
  `node apps/api/dist/worker.js`, or the queue fills without anything draining it.

## Kubernetes / PaaS

- Build the two images with `apps/api/Dockerfile` and `apps/web/Dockerfile`.
- Run the API with ≥ 2 replicas behind a load balancer with sticky sessions **or** a Socket.IO Redis
  adapter (the app already propagates cache invalidation through Redis pub/sub).
- Run one or more `worker` replicas (`node dist/worker.js`); jobs are idempotent and de-duplicated by job id.
- Expose `/api/v1/health` as the readiness probe.
- Use a managed MongoDB (Atlas) with backups enabled and a managed Redis.

## Reverse proxy checklist

- Forward `X-Forwarded-For` / `X-Forwarded-Proto`; set `TRUST_PROXY=true`.
- Allow WebSocket upgrade for `/socket.io/`.
- Cache `/assets/*` immutably; never cache `sw.js`, `manifest.webmanifest`, `index.html`.
- Raise `client_max_body_size` to at least `MAX_UPLOAD_MB`.

## Post-deploy

1. Log in as SUPER_ADMIN and change the password (Account settings → Password).
2. Website → Brand & SEO: set brand name, logo, contact, SEO, CTA.
3. Plans: review prices, modules and limits; set the default signup plan.
4. Platform settings → subscription: trial days, grace period, past-due behaviour, reminder days.
5. Feature flags: enable / disable platform features.
6. Platform settings → emergency: review the default emergency contacts copied into every new society.
7. Storage: with `STORAGE_DRIVER=local` mount a persistent volume for uploads (`imports/`, `incidents/`, `documents/`…); with S3 enable versioning.
8. Raise `MAX_UPLOAD_MB` (default 15) if societies import large spreadsheets or upload big documents; the reverse proxy limit must match.
